# 音视频会话服务（第一版）

这是一个不依赖 WebRTC、WebSocket 或外部通信平台的 Go 原型。两端通过进程内本地信箱交换提案，媒体数据由本地模拟源生成。

## 已实现

- 双方能力协商：轨道方向、编码、码率、采样率、声道数、分辨率必须落在双方共同范围内。
- 会话变更：新版本接受后整体替换活动轨道；停用或无交集的轨道不进入会话状态，相当于释放对应状态。
- 独立持久化：会话、轨道、协商版本分别写入 `sessions.json`、`tracks.json`、`versions.json`。
- 固定冲突规则：双方同时发起变更且已有待决版本时，按双方 ID 字典序较小者获胜；失败版本记录为 `superseded`。
- 版本保护：只有当前处于 `proposing` 的版本能接受答复；迟到答复返回 `stale`，不能覆盖新版本。
- 失败回滚：参数无共同范围时版本记录为 `rejected`，会话继续保留上一版活动轨道。
- 断开与恢复：对端离线时消息进入本地信箱，重连后按顺序投递，两端追平到同一协商版本。
- 多人参与世代：每个连接身份是一个 `Participation`（参与世代）。首次进入使用裸人名（`carol`），同名重入生成全新身份 `carol#2`，旧身份保留为 `present=false` 仅用于审计，绝不复用旧连接。
- 轨道来源：`TrackState` 同时携带 `Owner`（发布参与世代）与 `SourceID`（本地稳定来源编号）。重入者复用相同本地编号（如 `video-1`）时，`Owner=carol#2` 使其成为新来源，不会复活旧世代的轨道。
- 按参与者订阅：多人会话中每个目标世代独立答复、逐轨道接受；一条活动轨道的 `Subscribers` 恰好是明确接受且仍在场的世代。每端 `VisibleTracks()` 只返回自己明确接受且仍有效的来源，发布者可见自己的源。部分成员接受时版本为 `partially_accepted` 并持续收集答复，全部当前目标答复后才 `accepted`。
- 世代隔离：Bus 以参与世代为地址，离场即 `Unregister` 并丢弃排队消息；新世代不能答复旧世代才是目标的版本，离场者的迟到同意只记入 `DuplicateAnswer` 留档，不复活任何轨道，也不会把不同世代的同意拼成全体接受。
- 重复答复：版本关闭后的重复答复（含进程重启后从 JSON 重新加载）写入版本的 `duplicates` 留档，返回 `stale`，活动轨道保持不变。
- 模拟媒体：`LocalMediaSource` 只为当前活动轨道生成帧，帧携带 `Owner`/`SourceID`；后续可替换成真实 RTP/SRTP 或其他传输层。

## 运行

```bash
go test ./...
go run . -data /tmp/avsession-demo
```

两端演示会依次展示：

1. 交叉提案与固定规则冲突。
2. 旧版本迟到答复不能覆盖新版本。
3. 一端离线、消息排队、重连后停用视频并释放状态。
4. 编码无共同范围导致协商失败，但旧会话保持不变。

随后是多人会话演示：

5. Alice 发布音频+视频，Bob 全接受、Carol 仅接受音频（每端只看到自己接受的来源）。
6. Carol 离场后同名重入成为 `carol#2`：订阅清空、旧队列丢弃。
7. `carol#2` 复用本地编号 `video-1`：编号相同但来源标记为新世代。
8. 撤下视频与 Bob 的迟到同意同时发生：Bob 离场，其排队消息和迟到同意均无效，视频不恢复。
9. 旧身份消息不能影响新身份；重启服务后的重复答复只留档；历史决定可查，跨世代同意不拼成全体接受。

## 代码结构

- `model.go`：会话、轨道、能力、提案、协商版本和消息模型。
- `store.go`：原子 JSON 持久化，三类数据分开保存。
- `negotiate.go`：共同范围求交（发布者↔单个订阅者逐对）与轨道状态生成。
- `service.go`：会话版本机、参与世代管理、冲突裁决、逐参与者接受/拒绝、离场裁剪和回滚。
- `bus.go`：离线可恢复的进程内本地信箱。
- `endpoint.go`：模拟端如何发送/处理协商消息。
- `media.go`：本地模拟媒体帧与轨道/来源描述。
- `main.go` / `demo_data.go`：端到端演示和示例能力配置。
- `service_test.go`：关键一致性规则测试。

## 后续接入真实传输

第一版将协商状态与传输解耦。后续可以保留 `Service` 的版本机，把 `Bus` 和 `LocalMediaSource` 分别替换为实际信令通道与 RTP/SRTP 收发器；活动轨道以协商成功后持久化的 `TrackState` 作为传输配置来源。
